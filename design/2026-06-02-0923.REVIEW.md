This document converts the external security and performance review into an
implementation plan for OxideBBS. It is intentionally prescriptive. Coding
agents should implement the tasks as written, in phase order, without inventing
policy, thresholds, schemas, or alternative security models.

The source review raised forty findings. This plan preserves those finding
numbers so future work can be traced back to the original review.

2. Do not change thresholds, defaults, table names, config names, or policies

## Phase 3: Door Runtime Containment And Cleanup

Addresses findings: 6, 7, 8, 9, 15, 20, 30, 34.

Status: **Done in `c59047c`**.

Implemented:

- `[doors].allowed_runners` is a config-driven allowlist; door runner must
  be in the list. Resolved path must be a regular file, not world-writable,

## Phase 4: Data Correctness, Encoding, And Audit Policy

Addresses findings: 11, 13, 14, 18, 19, 36.

Status: **Done in `c59047c` (with one accepted deviation on 4.5)**.

Implemented:

- `alias_normalized UNIQUE` is the canonical alias uniqueness gate. New-user
  flow uses `insert_user_if_alias_available`; the DB rejects case-only
  duplicates at the unique constraint and the repository returns a typed
  `DuplicateAlias` error for the caller-friendly message.
- CP437 input validation rejects non-CP437 characters at subject, body,
  reply body, and non-hidden line input with the message "This BBS only
  accepts CP437-compatible text here." Password input is not subject to
  the check (it is hidden and never echoed).
- `ServerRuntime::audit_write_failures` is an `AtomicU64` that increments
  when runtime-aware audit write paths fail. `ControlStatus` includes the
  counter.
- `[audit].retention_days` config; `purge_audit_events_older_than` SQL
  helper exists. Runbook instructs operators to schedule maintenance.
- `insert_audit_event` uses server-side `GEN_RANDOM_UUID()` and
  `CURRENT_TIMESTAMP`; the prior two-step "scalar UUID + scalar NOW + insert"
  path is gone. `audit_door_event` no longer fetches UUIDs/timestamps from
  the client side.

### 4.5 User Login Counter Transaction — Accepted as-is

The original spec called for wrapping `update_user_login` in a transaction
or an explicit single-statement atomic update. The current code is a single
`UPDATE users SET last_login_at = $1, total_calls = total_calls + 1 WHERE
id = UUID_PARSE($2)` statement. DecentDB's single-writer model serializes
write transactions, so two concurrent `update_user_login` calls for the
same user are linearly ordered. The current single statement is atomic with
respect to other writers in the same DecentDB instance. **No code change
is required.** If the project ever moves to a multi-writer DecentDB
topology, this decision must be revisited and an explicit transaction
wrapper added.

## Phase 5: Telnet Transport And Caller I/O Performance

Addresses findings: 21, 22, 23, 24, 37, 40.

Status: **Done**.

Implemented:

- `TcpTransport` keeps a 4096-byte internal read buffer. `read_byte` refills
  the buffer when empty and yields one byte per call. EOF and error
  semantics are preserved. Two new unit tests verify multi-frame reads and
  the byte-at-a-time yield.
- `InputSession::pending_replies` accumulates telnet negotiation replies;
  `flush_pending_replies` coalesces them into one `write_all` before
  caller-visible output, before blocking on more input when replies are
  pending, and before hangup. The previous one-write-per-ack behavior is
  gone.
- `negotiate_terminal_capabilities` tracks terminal type and NAWS state and
  exits early when both have been received, while preserving the existing
  timeout and non-negotiation data escape paths.
- `drain_line_ending_after_menu_key` uses zero-duration immediate reads and
  pending input buffering instead of fixed 5 ms waits.
- `send_text_buffered` and `encode_text_into` reuse caller-local byte buffers,
  and ASCII text takes a direct byte-copy fast path before CP437 lookup.

Verification: `capability_negotiation_completes_before_timeout`,
`capability_negotiation_defaults_to_plain_text_without_response`,
`capability_negotiation_ends_on_real_data_without_losing_data`,
`menu_line_ending_drain_keeps_following_input`,
`menu_line_ending_drain_single_key_does_not_wait`, and
`ascii_text_encodes_without_cp437_lookup`.

## Phase 7: Low-Risk Follow-Ups And Load-Test Notes

Addresses findings: 4, 10, 31, 38, 39.

Status: **Resolved by reduction (4, 10); accepted as-is (31, 38, 39)**.

### 7.1 Login Failure Audit Write Amplification — Resolved

Finding 4 is reduced to negligible by Phase 1 (per-IP/per-alias rate
limiting) and Phase 4 (single-statement audit insert). No separate
process-side UUID cache is required. The rate limiter bounds the maximum
failed-login throughput, and the single-statement audit insert makes each
attempt's audit cost O(1) round-trips.

Verification: a focused micro-benchmark or a 60-second load test that
fires repeated bad logins confirms the audit table does not grow
unbounded and the rate limiter engages after the configured threshold.

### 7.2 Hard Link Staging Panic Leak — Resolved

Finding 10 is covered by the `DoorRuntimeDirectoryGuard` introduced in
Phase 3. The guard's `Drop` impl calls `cleanup_node_runtime_dir`, which
recursively removes the per-node runtime dir. The hard-link staging
function (`oxidebbs-door::stage_dosemu2_command`) creates files inside
this directory, so any panic between the hard-link/copy and the next
phase's success/failure path still triggers cleanup via the guard.

Verification: a new test forces a panic after the hard-link succeeds and
asserts that the runtime dir is empty afterward.

### 7.3 Config-Driven ANSI Terminal Allowlist — Accepted

Finding 31 is intentionally deferred. The current
`terminal_type_supports_ansi` function is a hardcoded allowlist. The
re-review did not flag this as a v1 concern. Do not add config-driven
terminal allowlists unless the user explicitly requests that after v1
security work.

### 7.4 CP437 Lookup Table Micro-Optimization — Accepted

Finding 38 is not a v1 target. No action unless profiling shows CP437
lookup dominates runtime. (See also NEW-9 in Phase 8 for the related
re-review concern about per-keystroke validation.)

### 7.5 Connection-Level Backpressure Load Test — Load test only

Finding 39 is behavior to validate, not a requested change.

The re-review confirms the existing behavior is correct: the accept loop
spawns a task for every accepted TCP connection, but only `nodes.count`
of them will hold a `NodeAllocation`. The `(nodes.count + 1)`-th caller
is rejected with `System is busy. Please try again later.` after the
accept. This is the right behavior; just verify it under load.

Required load-test note:

- A manual or automated load test that opens `max_connections + 1`
  concurrent TCP connections and confirms the extra caller is rejected
  while all accepted node slots remain stable and controllable through
  `nodes list`.

Do not change accept/rejection behavior unless that test fails.

### NEW-1: Control-socket authorization is peer-UID-strict

**Severity: Medium (operational/UX).**

Status: **Done via Option 1**. `design/RUNBOOK.md` and
`docs/project/sysop-cli.md` document that control-socket CLI commands must run
as the same UID as the server process, with a concrete `sudo -u oxidebbs
oxidebbs-server nodes list` example.

**Context.** Phase 2.1 implemented `is_authorized_control_uid`, which
only accepts connections whose peer UID matches the server's effective
UID. This is the right security model — the filesystem mode `0600` and
runtime dir mode `0700` are not the only gate; the server is also
checking identity. But the current implementation has no escape hatch:

- A sysop running `oxidebbs-server nodes list` via `sudo -u bbsbbs` from a
  different login shell works.
- A sysop running the CLI as `root` (a common pattern for system
  administration) is denied with `control socket access denied for peer
  uid 0 (expected <bbs_uid>)`.
- A sysop using `doas`, `su`, or a systemd user manager with a different
  UID is also denied.

Before this update, the runbook (in `design/RUNBOOK.md` and
`docs/project/sysop-cli.md`) explained the model but did not call out the
operational consequence that the CLI must run as the same user that owns the
BBS process.

**Why it matters.** Without an explicit `sudo -u bbsbbs oxidebbs-server
...` wrapper, an operator may waste hours debugging "permission denied"
on a socket they can see and read the mode of. The current error message
identifies the UID mismatch, but only after the operator reads it
carefully.

**Recommended fix.** Three layered options, in order of preference:

1. **Document the requirement.** Update `design/RUNBOOK.md` and
   `docs/project/sysop-cli.md` with an explicit "the CLI must run as the
   same user as the server" callout, with concrete examples for `sudo
   -u bbsbbs oxidebbs-server nodes list`. This is the minimum acceptable
   for v1.
2. **Add a config-driven allowlist of additional UIDs/gids.** Extend
   `OxideConfig` with a `[control].allowed_peer_uids: [u32]` and/or
   `[control].allowed_peer_gids: [u32]`. The check becomes
   `peer_uid == server_uid || allowed_peer_uids.contains(peer_uid) ||
   peer_gids.intersects(allowed_peer_gids)`. This is the right answer
   for multi-user or sudo-based administration.
3. **Add a shared-secret token.** Out of scope per ADR 0015; explicitly
   deferred.

**Acceptance tests:**

- (Option 1) The runbook/sysop-cli docs contain a "must run as server
  UID" section with at least one concrete example.
- (Option 2) With `allowed_peer_uids = [0]`, a CLI run as root succeeds.
  With `allowed_peer_uids = []` (the default), the CLI must run as the
  server UID. The `[control]` config section is documented in
  `config/oxidebbs.example.toml`.
- The existing `control_socket_round_trip` test still passes.

### NEW-2: Door runner ownership check is at validation time, not spawn time

**Severity: Low to Medium (TOCTOU window is microseconds in practice).**

Status: **Done**. `DoorSessionService::execute_interactive` re-runs
`validate_door_runner` immediately before `Command::spawn`; a failed recheck
finalizes the run with an audited note and a caller-safe launch failure.
`runner_revalidation_detects_permission_change_before_spawn` covers the
permission-change case.

**Context.** `validate_door_runner_security` in
`crates/oxidebbs-server/src/door_session.rs` runs the canonicalize +
ownership check during `validate_door`, which is called from
`execute_interactive` *before* `Command::spawn`. Between validation and
spawn, the on-disk runner could in theory be replaced (or have its
permissions changed) by a privileged local user. The validate-then-spawn
window is microseconds, and the runtime dir is mode `0700` so the door
itself cannot modify its parent process's view of the filesystem, but a
cooperating root user could.

**Recommended fix.** Re-check the runner's file metadata immediately
before `Command::spawn` (i.e. inside `execute_interactive`, after
`build_request` and before `command.spawn()`). If the metadata has
changed in a way that would have failed validation (different owner,
group/world writable, no longer a regular file), refuse to launch. Log
the change to the audit log.

A lighter alternative: stat the resolved path right before `spawn()` and
assert the inode is the same as what `validate_door` saw. If different,
refuse to launch.

**Acceptance tests:**

- A test that swaps the runner file (or chmods it world-writable) between
  `validate_door` and `spawn` is rejected with an error logged to the
  audit table and a friendly message to the caller.
- Existing door dry-run tests still pass.

### NEW-3: `AuditEventRecord` struct has dead `id` and `created_at` fields

**Severity: Low (maintenance hazard, not a correctness bug).**

Status: **Done via Option B**. `id` and `created_at` remain because preserving
import/export paths legitimately use them. The fields are marked `#[doc(hidden)]`
and documented as list/export and preserving-import fields ignored by normal
runtime inserts. `runtime_insert_returns_generated_id_and_timestamp` verifies
that DecentDB still returns generated IDs and timestamps.

**Context.** Phase 4.4 changed `insert_audit_event` to use
`GEN_RANDOM_UUID()` and `CURRENT_TIMESTAMP` server-side. The Rust struct
`AuditEventRecord { pub id: String, pub created_at: String, ... }` still
has those two fields, and `audit_door_event` passes empty strings into
them. The fields are ignored at the DB layer. This works but is a
maintenance hazard: a future developer reading `audit_door_event` will
think the empty strings are a bug.

**Recommended fix.** Either:

- **Option A:** Remove `id` and `created_at` from `AuditEventRecord` and
  update every call site. `list_audit_events` already returns
  `UUID_TO_STRING(id)` and `CAST(created_at AS TEXT)`, so the SELECT
  path is fine; it's the INSERT struct that is misleading.
- **Option B:** Mark the fields with `#[serde(skip)]` (if applicable)
  and `#[doc(hidden)]` so they don't show up in autocomplete, and add a
  `// Note: id and created_at are server-generated; do not set from
  Rust.` comment.

Option A is the right long-term answer. Option B is acceptable for v1
if the call sites are too numerous to update atomically.

**Acceptance tests:**

- (Option A) `cargo check` and all tests pass with `id` and
  `created_at` removed from `AuditEventRecord`.
- `list_audit_events` still returns populated id/timestamp columns.
- A test creates an audit event and confirms the returned record has a
  non-empty id and timestamp.

### NEW-4: `audit_write_failures` counter undercounts

**Severity: Low (operational visibility, not a correctness bug).**

Status: **Done**. `emit_audit_event_with_runtime` threads
`Option<&ServerRuntime>` through runtime-owned audit paths, including login,
caller lifecycle, server start/stop, node assignment, new-user creation, door
unavailable events, and database-write failure audits. The config-loaded audit
event is intentionally emitted before runtime creation and therefore cannot
increment the runtime counter. `runtime_counter_increments_when_audit_insert_fails`
covers the forced-failure path.

**Context.** The re-review found that `ServerRuntime::record_audit_write_failure`
was called from door audit paths and one server audit path, while several
runtime-owned audit paths only warned and continued.

**Recommended fix.** Thread `Option<&ServerRuntime>` (or an
`AuditRecorder` trait object) through every `emit_audit_event` and
`emit_db_write_failed_event` call site. The pattern already exists for
the door path (`runtime: Option<&ServerRuntime>` parameter on
`insert_started_run`, `finish_run`, `audit_door_event`); extend it to
`serve.rs`'s `emit_audit_event` and `emit_db_write_failed_event`.

Alternatively, store the runtime inside the `OxideDb` wrapper or a
context struct so it is always available without threading.

**Acceptance tests:**

- A test that forces an audit insert failure (e.g. by passing a malformed
  `user_id` that fails `UUID_PARSE`) increments the counter.
- The `control_status_json_includes_audit_write_failures` test still
  passes.
- `ControlStatus` JSON shows a non-zero counter after the forced failure.

### NEW-5: New-user flow could use atomic `INSERT ... ON CONFLICT`

**Severity: Very Low (cosmetic / defense-in-depth).**

Status: **Done**. `insert_user_if_alias_available` uses an atomic
`INSERT ... ON CONFLICT (alias_normalized) DO NOTHING RETURNING id` repository
path and maps duplicate rows to `UserInsertError::DuplicateAlias`. The new-user
flow uses this function and still surfaces "That alias is already in use."
for callers. Duplicate, case-only duplicate, and same-handle concurrent
duplicate tests cover the typed error.

**Context.** Before this phase, `run_new_user_flow` did
`find_user_by_alias_ci(...)?.is_some()` then `insert_user(...)`. The
unique constraint on `alias_normalized` already enforced correctness at
the DB layer, but it emitted two DB round-trips for what could be one.

**Recommended fix.** Add an `insert_user_if_alias_available` repository
function (the original Phase 4.1 spec called for this and it was not
implemented in `c59047c`). Use `INSERT INTO users ... ON CONFLICT
(alias_normalized) DO NOTHING RETURNING id` and check whether a row was
returned. If not, surface a typed `DuplicateAlias` error to the caller.

This was **not blocking** for v1 because the previous unique constraint still
preserved correctness, but implementing the atomic insert removed a small
TOCTOU and a round-trip.

**Acceptance tests:**

- A race where two `run_new_user_flow` calls with the same alias run
  concurrently results in exactly one successful insert and one
  `DuplicateAlias` error returned to the second caller.
- Existing new-user flow tests still pass.
- The friendly duplicate message ("That alias is already in use.")
  still surfaces to the caller.

### NEW-6: Runtime dir `chmod 0700` may fail on pre-existing directories

**Severity: Low (operational edge case).**

Status: **Done via Option 1**. `design/RUNBOOK.md` and
`docs/project/sysop-cli.md` document that `paths.runtime` and pre-existing
`runtime/node-NNN` directories must be writable/chown-able by the server UID,
mode `0700`, and stale node directories should be removed before restarting
under a different user.

**Context.** `prepare_node_runtime_dir` now does
`fs::set_permissions(&dir, fs::Permissions::from_mode(0o700))` after
`create_dir_all`. If the directory already existed with mode `0755` and
the BBS runs as a non-root user, the chmod may fail with `EPERM` on
some filesystems (notably NFSv4 with root_squash, or when the directory
is owned by a different UID). The current code propagates the error
through `DoorError::Io`, which surfaces as a friendly "Door runtime
directory ... is not writable" message to the caller. This is correct
behavior, but before this update it was not documented and could surprise
operators.

**Recommended fix.** Three layers, in order of preference:

1. **Document the requirement.** The runbook and `paths.runtime` docs
   should state that the runtime dir (and any pre-existing subdirectories
   the BBS creates inside it) must be writable and chown-able by the
   server UID. Pre-existing `runtime/node-NNN` directories from a
   previous install should be removed before restarting under a new
   user.
2. **Treat pre-existing wrong-mode dirs as fatal at startup.** Add a
   startup check that walks `paths.runtime` and refuses to serve if any
   `node-NNN` subdirectory has permissions wider than `0700` or is
   owned by a UID other than the server's effective UID.
3. **Best-effort chmod with a warning.** Change
   `prepare_node_runtime_dir` to attempt the chmod but log a `warn!` and
   continue if it fails. This is the loosest policy and is not
   recommended for v1.

**Acceptance tests:**

- (Option 1) The runbook/sysop-cli docs call out the chmod requirement.
- (Option 2) A test that pre-creates a `runtime/node-001` dir as a
  different UID sees the server refuse to start with a clear error.
- (Option 3) A test that pre-creates a `runtime/node-001` dir as a
  different UID with mode `0755` sees the door run proceed and the
  warning logged.

### NEW-7: Expired `auth_attempts` rows accumulate forever

**Severity: Low (operational; will grow over time).**

Status: **Done via Layer 1**. `is_auth_scope_locked` eagerly clears an expired
locked row for the checked scope/key and returns `false`. The v1 implementation
does not add a scheduled purge task because the layer-1 read cleanup satisfies
the finding. `expired_lockout_is_removed_on_lock_check` covers the cleanup.

**Context.** `is_auth_scope_locked` returns `true` if
`locked_until > now` and `false` otherwise. `find_auth_attempt` does
not filter on expiry; expired rows are simply ignored at read time.
There is no scheduled cleanup. A board that sees a steady stream of
brute-force attempts will accumulate `auth_attempts` rows indefinitely
with `failed_count = 0` (after a successful login clears the row) or
with `locked_until` in the past (after a lockout expires).

The DB has an index on `(scope, scope_key)` (PRIMARY KEY), so reads are
fine. The table will grow linearly with attacker effort, not with
legitimate user base. Over a year, a moderately attacked board may
accumulate hundreds of thousands of stale rows.

**Recommended fix.** Two layers:

1. **Eager cleanup on read.** Change `is_auth_scope_locked` to also
   `DELETE FROM auth_attempts WHERE locked_until IS NOT NULL AND
   locked_until <= $now` (or, less aggressively, just
   `locked_until <= $now`) as part of the lock check. This keeps the
   table bounded by the set of *currently locked* attempts plus a
   small grace period.
2. **Scheduled cleanup.** Add a runtime counter / background task that
   periodically (`request_auth_attempts_purge`) deletes rows where
   `locked_until IS NOT NULL AND locked_until <= now() -
   interval '1 hour'`. Expose this through the control socket
   (`nodes purge_stale_attempts` or similar).

Layer 1 is sufficient for v1. Layer 2 is a defense-in-depth add for
boards that see heavy brute-force traffic.

**Acceptance tests:**

- After an `auth_attempts` row's `locked_until` is in the past, the next
  `is_auth_scope_locked` call returns `false` AND the row is removed.
- A successful login still clears both `ip` and `alias` rows.
- The `record_auth_failure` transactional path still works.

### NEW-8: `clear_auth_attempt` is not in a transaction

**Severity: Very Low (acceptable in practice; documented for the record).**

Status: **Done**. `auth_repo` documents that DecentDB serializes
single-statement writes, so `clear_auth_attempt` is intentionally a single
atomic `DELETE`; the note requires revisiting this if OxideBBS ever adopts a
multi-writer DecentDB topology.

**Context.** `record_auth_failure` opens a transaction and commits the
failure insert. `clear_auth_attempt` is a single `DELETE` statement
without an explicit transaction wrapper. In DecentDB's single-writer
model, a single `DELETE` is atomic with respect to other writers. The
clear-after-success path does not race with the failure path
semantically — a single login attempt either succeeds (clears) or
fails (records) but not both. So this is fine in practice.

**Recommended fix.** No code change required. Document the decision in
the `auth_repo` module-level comment so a future multi-writer DecentDB
topology is forced to revisit it.

**Acceptance tests:** None required. This finding is documentation-only.

### NEW-9: Per-keystroke CP437 validation in `read_line_input`

**Severity: Low (performance; UX-correct but CPU-warm).**

Status: **Done**. `is_cp437_compatible` now returns immediately for ASCII text
before calling `encode_cp437`, and `encode_text_into` also copies ASCII output
directly. `ascii_is_cp437_compatible`, `ascii_text_encodes_without_cp437_lookup`,
and the existing emoji rejection tests cover the behavior.

**Context.** Phase 4.2 added CP437 validation at multiple input sites
(message subject, message body, reply body, line input for non-hidden
fields). The line-input validation in `read_line_input` calls
`is_cp437_compatible(&value)` after every keystroke (specifically, after
the buffer is flushed at Enter). The check itself is O(n) over the
line and walks the 128-entry CP437 high table per character.

For a fast typist on a 50-character line, the final validation walks
~50 characters through the table once at Enter time. The check is also
called in `is_cp437_compatible` which is `encode_cp437(text).is_ok()`,
which iterates the string again. Net cost: ~100 CP437 table lookups per
line for an ASCII-only typist.

**Recommended fix.** Two layers:

1. **Tighten the validation site.** The current per-line check is at the
   right granularity. Keep it.
2. **Cheaper ASCII fast path.** `is_cp437_compatible` currently does
   `encode_cp437(text).is_ok()`. Add a fast path: if every byte in
   `text` is ASCII (i.e. the high bit is never set), return `true`
   immediately without walking the high table. This makes the check
   O(n) over bytes instead of O(n) over chars through a 128-entry
   table.

```rust
fn is_cp437_compatible(text: &str) -> bool {
    if text.is_ascii() {
        return true;
    }
    encode_cp437(text).is_ok()
}
```

**Acceptance tests:**

- ASCII-only text returns `true` from `is_cp437_compatible` without
  touching the CP437 high table.
- Existing CP437 box-drawing tests still pass.
- Emoji input is still rejected.

### NEW-10: `validate_door` error message echoes host path to caller

**Severity: Medium (information disclosure to authenticated caller).**

Status: **Done**. `run_doors_flow` sends a generic caller-facing
"This door is not available right now. Contact the sysop." message for
`validate_door` failures while logging and auditing the verbose validation
details. Launch-error summaries also hide host paths from caller text.
`launch_error_summary_hides_verbose_host_details_from_caller` covers the
summary path.

**Context.** Phase 3.2 implemented the `working_dir` containment check
using `canonicalize` + `starts_with(&doors_root)`. The validator error message
includes `working_dir.display()` and `self.config.paths.doors.display()`. Before
this update, the caller-facing path could surface those details to an
authenticated caller, allowing them to learn host filesystem layout such as
`/var/lib/oxidebbs/doors/...` from a friendly "Door X working directory Y is
outside paths.doors Z" message.

**Recommended fix.** Two layers:

1. **Caller-facing message: generic.** Change
   `run_doors_flow`'s handling of `validate_door` errors to send a
   generic "This door is not available right now. Contact the sysop." to
   the caller. Keep the verbose error (with full path) in the audit
   log and the door's `launch_error` summary, which only the sysop sees.
2. **No code change in `validate_door` itself.** The function should
   continue to return the verbose error to the door service, which
   decides what to expose to the caller. The fix is in the caller-facing
   path, not in the validator.

**Acceptance tests:**

- A door with `working_dir` outside `paths.doors` returns a generic
  "not available" message to the caller.
- The audit log records the verbose error with the full path.
- Existing door validation tests still pass.
